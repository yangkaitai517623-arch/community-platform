# 青青社区便民服务平台进度与维护记录

本文档用于持续记录项目完整性、真实服务平台应具备的业务能力、当前欠缺点和每次修改内容。后续每次修改业务逻辑、接口、数据库或前端页面，都需要在“维护日志”中追加记录。

## 1. 项目目标

青青社区便民服务平台面向社区居民、维修师傅、跑腿接单人和后台管理员，包含前台用户端与后台管理端。目标不是简单 CRUD，而是形成可演示、可解释、业务闭环相对完整的社区服务系统。

核心业务包括：
- 跑腿需求：发布、AI 分类、接单、取消接单、进行中、完成、评价、后台管理。
- 检修需求：发布、AI 分类、居民接单、管理员分配维修师傅、师傅忙闲控制、取消/回退、完成确认、评价。
- 二手商品：发布、审核、AI 估价、购买、卖家确认、买家确认收货、取消订单。
- 论坛资讯：发布、浏览量、评论、点赞/取消点赞、后台审核。
- 用户权限：普通用户、管理员、超级管理员、维修师傅等角色权限隔离。
- 通知：需求接单、分配、改派、取消、完成等关键事件通知相关用户。

## 2. 真实平台应具备的业务能力

### 2.1 用户与权限
- 普通用户只能操作自己的资料、自己发布的内容、自己接的单。
- 管理员可以管理普通用户和业务内容，但不能任命管理员或超级管理员。
- 超级管理员可以调整用户角色、管理管理员和超级管理员。
- 权限必须在后端兜底，不能只依赖前端隐藏按钮。

### 2.2 跑腿业务
- 待接单需求对所有普通用户可见。
- 一旦被接单，只能被发布者和接单者看到。
- 接单者可以取消接单，需求回退为待接单。
- 已完成订单只对发布者和接单者可见。
- 管理员可以查看、删除、必要时调整状态，但状态变更必须同步接单人和订单表。
- 同一个接单人不能同时持有多个未完成跑腿任务。

### 2.3 检修业务
- 普通居民可以接单，也可以取消接单。
- 管理员可以分配维修师傅；维修师傅角色应与普通居民区分。
- 同一维修师傅不能同时被分配多个未完成检修任务。
- 发布者确认完成后，师傅释放，可以继续分配新任务。
- 状态回退为待接单时必须清空 `workerId` 并删除或释放活动订单记录。

### 2.4 二手商品与订单
- 商品发布后待审核，审核通过后才能购买。
- 买家下单后商品应被占用，避免重复下单。
- 卖家确认订单，买家确认收货，最终完成。
- 待确认订单可取消；取消后商品恢复在售。
- 商品状态和订单状态必须统一定义，避免数据库、后端、前端状态码不一致。

### 2.5 论坛资讯
- 浏览量允许重复累计。
- 点赞必须一人一次，再次点击取消点赞。
- 评论数以后端已发布评论数量为准。
- 后台可以审核、下架、删除帖子和评论。

### 2.6 AI 能力
- 基础任务：发布跑腿/检修需求时，AI 提取服务类型、紧急程度和技能标签。
- 匹配增强：根据 AI 标签和师傅忙闲状态推荐合适服务者。
- 进阶任务：二手商品估价应检索历史同类成交记录，再结合大模型生成估价区间和优化描述。
- AI 调用失败时必须有规则兜底，不能阻断主业务。

## 4. 数据库脚本与运行要求

已有数据库需要按需执行：
- `database/add-forum-like.sql`：新增论坛点赞记录表，保证一人一次点赞。
- `database/fix-goods-order-status-comment.sql`：统一商品订单状态注释。
- `database/check-request-order-consistency.sql`：只读检查跑腿/检修需求与订单数据是否一致。
- `database/add-request-order-unique-key.sql`：给 `repair_order.request_id` 和 `errand_order.request_id` 添加唯一约束，避免同一需求生成多条订单。
- `database/backfill-request-orders.sql`：回填旧数据中缺失的 `repair_order` / `errand_order` 记录，解决历史已接单/已完成需求在订单页、评价、统计中查不到订单的问题。
- `database/localize-notification-messages.sql`：把旧数据库中已经生成的英文服务通知批量改为中文。

执行 `add-request-order-unique-key.sql` 前请确认：
- 本地已有历史重复订单时，脚本会保留较早记录、删除重复记录。
- 脚本已经改成可重复执行；如果索引已存在，会输出提示，不会重复添加。
- 新库如果已经使用最新 `schema.sql` 创建，通常不需要重复执行。

推荐旧库执行顺序：
1. 先执行 `database/check-request-order-consistency.sql`，确认当前缺哪些数据。
2. 再执行 `database/backfill-request-orders.sql`，补齐历史服务订单。
3. 再执行 `database/add-request-order-unique-key.sql`，清理重复订单并加唯一约束。
4. 最后再执行一次 `database/check-request-order-consistency.sql`，确认缺失订单和重复订单已经清掉。
5. 重启后端，在前端重新测试跑腿/检修完成评价、后台订单页和仪表盘统计。
